Restrições e bloqueios são os dois mecanismos que impedem um projeto de estar onde não deveria. Eles resolvem problemas diferentes:

<CardGroup cols={2}>
<Card title="Restrição" icon="shield">
  Vive na etapa e olha para o **movimento**. Define de onde o projeto pode chegar e para onde pode sair, com base em critérios que ele precisa cumprir.
</Card>

<Card title="Bloqueio" icon="ban">
  Vive no status ou na etiqueta e olha para a **combinação**. Impede que um projeto com aquela marca ocupe determinadas etapas.
</Card>
</CardGroup>

Restrições e bloqueios só podem ser configurados depois que o funil foi salvo pelo menos uma vez.

## Restrições

Uma restrição limita a entrada ou a saída de uma etapa, permitindo o movimento apenas quando o projeto cumpre o critério estabelecido. Você as configura no botão **Restrições** da etapa.

### Direção

Toda restrição vale para uma direção: a entrada ou a saída da etapa.

<Tabs>
<Tab title="Entrada">
  Vale quando o projeto está chegando nesta etapa. Responde à pergunta: "o que precisa ser verdade para o projeto poder entrar aqui?"

  Exemplo: só entra em "Em desenvolvimento" quem vem de "Aprovado".
</Tab>

<Tab title="Saída">
  Vale quando o projeto está deixando esta etapa. Responde à pergunta: "o que precisa ser verdade para o projeto poder sair daqui?"

  Exemplo: só sai de "Proposta" quem está com o status "Proposta aceita".
</Tab>
</Tabs>

### Tipos de restrição

Existem quatro tipos de restrição, cada um com um critério diferente.

<AccordionGroup>
<Accordion title="Restrição para etapa" icon="diagram-project">
  Amarra o movimento a uma etapa específica.

  Na **entrada**, exige que o projeto venha da etapa indicada. Na **saída**, exige que ele esteja indo para a etapa indicada.

  <Note>
  A restrição de entrada por etapa é ignorada quando o projeto está ocupando mais de uma etapa ao mesmo tempo, porque nesse caso não existe uma origem única. Isso só acontece em funis com múltiplas etapas.
  </Note>
</Accordion>

<Accordion title="Restrição para etiqueta" icon="tag">
  Exige que o projeto tenha uma etiqueta específica do funil.

  Exemplo: só entra em "Atendimento prioritário" quem tem a etiqueta "Cliente enterprise".
</Accordion>

<Accordion title="Restrição para status do funil" icon="circle-half-stroke">
  Exige que o projeto esteja com um status específico naquele funil.

  Exemplo: só sai de "Aguardando aprovação" quem está com o status "Aprovado".
</Accordion>

<Accordion title="Restrição de decisão" icon="filter">
  Em vez de um único critério, usa um **filtro salvo** — o mesmo tipo de filtro que você monta na busca avançada de projetos, com quantas condições quiser.

  Ela também pode avaliar a hierarquia do projeto em movimento, e não só o próprio projeto.
</Accordion>
</AccordionGroup>

### Escopo da hierarquia

Só existe na restrição de decisão. Define **sobre quais projetos** o filtro é avaliado.

| Escopo | O que é avaliado |
| --- | --- |
| Projeto atual | Apenas o projeto que está sendo movido |
| Descendentes | Os projetos filhos, netos e bisnetos, conforme a profundidade escolhida |
| Ancestrais | O projeto pai, avô e bisavô, conforme a profundidade escolhida |

Quando o escopo é hierárquico, você escolhe até onde ir: todos os níveis, apenas filhos diretos, até netos (2 níveis) ou até bisnetos (3 níveis). O mesmo vale para ancestrais.

A restrição só é aprovada se **todos** os projetos do escopo atenderem ao filtro. Se um único descendente não atender, o movimento é recusado.

Se não houver nenhum projeto no escopo, a restrição é considerada atendida. É o caso de um projeto sem filhos com escopo "descendentes".

<Tip>
Para implementar "a entrega só avança quando todas as subtarefas estiverem concluídas", crie uma restrição de saída com escopo descendentes e um filtro salvo que verifica o status de conclusão.
</Tip>

Para entender vínculos pai e filho, veja [Hierarquia de projetos](/guides/projects/project-hierarchy).

### Como várias restrições se combinam

Esta regra vale um minuto de atenção: a forma como várias restrições se combinam depende do tipo delas.

| Tipo | Combinação | Leitura |
| --- | --- | --- |
| Etapa | Pelo menos **uma** precisa ser atendida | "pode vir de A **ou** de B" |
| Status do funil | Pelo menos **uma** precisa ser atendida | "pode estar com o status X **ou** Y" |
| Decisão (filtro) | Pelo menos **uma** precisa ser atendida | "atende ao filtro A **ou** ao filtro B" |
| Etiqueta | **Todas** precisam ser atendidas | "precisa ter a etiqueta X **e** a etiqueta Y" |

Entre tipos diferentes a exigência é sempre conjunta: se a etapa tem restrições de etapa e de etiqueta, os dois grupos precisam ser aprovados.

<Tip>
Se você quer "precisa ter pelo menos uma dessas etiquetas", a restrição por etiqueta não serve, porque ela exige todas. Use uma restrição de decisão com um filtro salvo que aceite qualquer uma delas.
</Tip>

### Dando nome às restrições

O nome da restrição é opcional, mas vale o esforço: é ele que aparece para quem teve a movimentação recusada. Uma recusa com o nome "Só entra com proposta assinada" diz à pessoa o que fazer; o texto genérico "Restrições de entrada", não.

<Note>
Restrições de etapa ativas contam no limite de uso da conta. Quando a conta já está no limite, a nova restrição é salva inativa.
</Note>

## Bloqueios de etapa

O bloqueio parte do outro lado: em vez de configurar a etapa, você configura o **status** ou a **etiqueta** e escolhe em quais etapas aquela marca não é permitida. A opção se chama **Bloquear vínculo nas etapas**.

A lista começa pelas etapas do próprio funil. Marque **Mostrar etapas de todos os funis** para bloquear também etapas de outros funis.

Exemplo: a etiqueta "Bloqueado pelo cliente" não pode conviver com as etapas "Em produção" e "Em entrega".

### O bloqueio vale nos dois sentidos

O bloqueio age em dois momentos.

<CardGroup cols={2}>
<Card title="Ao mover o projeto" icon="arrow-right">
  Um projeto que já carrega o status ou a etiqueta bloqueada não consegue entrar na etapa.
</Card>

<Card title="Ao aplicar a marca" icon="tag">
  Um projeto que já está na etapa não consegue receber o status ou a etiqueta bloqueada.
</Card>
</CardGroup>

### Bloquear vínculo por automações

Ao selecionar as etapas bloqueadas, cada uma oferece a opção **Bloquear vínculo por automações**. Ela define se o bloqueio também vale para as automações.

| Opção | Efeito |
| --- | --- |
| Marcada | Nem as automações conseguem aplicar aquele status ou etiqueta em um projeto que está na etapa bloqueada. |
| Desmarcada | Automações conseguem aplicar a marca mesmo com o bloqueio ativo. Pessoas continuam bloqueadas. |

<Note>
Essa opção vale para a aplicação do status ou da etiqueta. A movimentação de um projeto para uma etapa bloqueada é recusada em qualquer caso, inclusive quando feita por automação.
</Note>

## Quando usar restrição ou bloqueio

A escolha depende do tipo de regra.

<CardGroup cols={2}>
<Card title="Use restrição quando" icon="shield">
  A regra é sobre o caminho: de onde vem, para onde vai, o que precisa estar preenchido ou decidido para o projeto se mover.
</Card>

<Card title="Use bloqueio quando" icon="ban">
  A regra é sobre incompatibilidade: existe um estado do projeto que não combina com determinadas etapas, não importa por onde ele passou.
</Card>
</CardGroup>
