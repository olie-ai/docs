A ação **Criar hierarquia de projetos** cria ou vincula projetos filhos abaixo de um projeto pai, montando a árvore inteira de uma vez. Esta página mostra como configurar a ação, como escrever a estrutura e exemplos prontos para adaptar. Para entender os níveis e as regras da hierarquia em si, veja [Hierarquia de projetos](/guides/projects/project-hierarchy).

O projeto pai é o projeto que acionou o gatilho da automação, e ele não entra na estrutura. Se você definir outros [projetos alvo](/guides/automation/anatomy#em-quais-projetos-cada-componente-age) na ação, a estrutura é criada em cada um deles.

## Quando usar

Use esta ação quando um tipo de trabalho sempre se desdobra em partes conhecidas. Por exemplo:

- todo contrato aprovado vira as frentes de levantamento, execução e validação;
- toda implantação ganha um projeto por módulo contratado;
- a estrutura depende de dados do projeto pai, como o cliente ou o orçamento.

## Configurar a ação

A ação tem três decisões: criar ou vincular, usar ou não um modelo de projeto e para qual etapa enviar os projetos marcados.

### 1. Criar ou vincular projetos

A opção **Criar ou vincular projetos?** define o que acontece com cada linha da estrutura.

| Opção | O que faz |
| --- | --- |
| Criar projetos | Cria projetos filhos novos, do zero ou a partir de um modelo de projeto |
| Vincular projetos existentes | Conecta projetos já criados ao projeto pai, sem criar projetos novos. Serve para reorganizar |

Para vincular projetos existentes, escreva em cada linha da estrutura o código do projeto, como `PRJ-42`. A ação também aceita o ID do projeto, mas não procura pelo nome. Todos os projetos da lista viram filhos diretos do projeto pai: nesse modo, os hífens não criam netos. Se algum código não corresponder a um projeto da empresa, a ação para e registra `project_not_found_for_attach`.

### 2. Projeto modelo (opcional)

Com um [modelo de projeto](/guides/projects/project-templates) selecionado, cada filho criado é uma cópia do modelo. Veja [o que vai junto](/guides/projects/project-templates#o-que-vai-junto) na cópia.

Sem modelo, os projetos são criados do zero, só com as configurações básicas.

### 3. Etapa de destino (opcional)

A etapa de destino recebe só os projetos marcados com o prefixo `>` na estrutura. Os projetos sem `>` não são vinculados a essa etapa, mesmo com uma etapa selecionada.

## Escrever a estrutura

A estrutura é um texto com um projeto por linha. O prefixo no começo da linha indica o nível do projeto. Linhas em branco são ignoradas:

```text
Contrato
Implantação
-Configuração
-Treinamento
--Turma da manhã
Suporte inicial
```

Cada neto fica abaixo do último filho que aparece antes dele, e cada bisneto fica abaixo do último neto. No exemplo acima, "Configuração" e "Treinamento" são filhos de "Implantação", e "Turma da manhã" é filho de "Treinamento".

### Prefixos

A tabela mostra os prefixos aceitos:

| Prefixo | Significado | Exemplo |
| --- | --- | --- |
| Nenhum | Filho direto do projeto pai | `Contrato` |
| `-` | Neto: filho do último filho acima | `-Configuração` |
| `--` | Bisneto: filho do último neto acima | `--Turma da manhã` |
| `>` | Vincula o projeto à etapa de destino. Combina com os níveis | `>Contrato`, `->Configuração`, `-->Turma da manhã` |

O espaço entre o prefixo e o nome é opcional: `--Turma da manhã` e `-- Turma da manhã` dão o mesmo resultado. Duas regras de escrita importam:

- os hífens de um nível ficam colados. Em `- - Turma da manhã`, só o primeiro hífen conta como nível, e o projeto se chama "- Turma da manhã";
- o `>` vem depois dos hífens, como em `->Configuração` ou `- > Configuração`.

## Exemplos

Os exemplos abaixo mostram a estrutura escrita na ação e a árvore que ela cria.

### Filhos diretos

Uma estrutura sem prefixos cria só filhos:

```text
Contrato
Implantação
Treinamento
```

Resultado:

```text
[Projeto pai]
├── Contrato
├── Implantação
└── Treinamento
```

### Filhos e netos

Um hífen coloca o projeto abaixo do último filho:

```text
Levantamento
Execução
-Frente A
-Frente B
```

Resultado:

```text
[Projeto pai]
├── Levantamento
└── Execução
    ├── Frente A
    └── Frente B
```

### Vários filhos com netos

Cada grupo de netos fica abaixo do filho que vem logo antes:

```text
Frontend
-Componentes
-Páginas
Backend
-API
-Banco de dados
Testes
-Qualidade
```

Resultado:

```text
[Projeto pai]
├── Frontend
│   ├── Componentes
│   └── Páginas
├── Backend
│   ├── API
│   └── Banco de dados
└── Testes
    └── Qualidade
```

### Com etapa de destino

Só as linhas com `>` vão para a etapa de destino:

```text
>Levantamento
Execução
>Validação
-Relatório final
```

Resultado:

- "Levantamento" e "Validação" são vinculados à etapa de destino escolhida na ação.
- "Execução" e "Relatório final" não são vinculados a essa etapa.

## Usar sintaxe avançada

O campo de estrutura aceita [variáveis e sintaxe avançada](/guides/automation/variables). Assim, a árvore pode repetir blocos, depender de condições ou usar dados do projeto pai.

<Tabs>
<Tab title="Repetição">
  Um laço `for` repete o mesmo bloco várias vezes:

  ```twig
  {% for i in 1..3 %}
  {{ project.name }} - Sprint {{ i }}
  -{{ project.code }} Planejamento
  -{{ project.code }} Desenvolvimento
  -{{ project.code }} Revisão
  {% endfor %}
  ```

  Para um projeto pai chamado "Portal do cliente", com código `P1`, o resultado é:

  ```text
  [Portal do cliente]
  ├── Portal do cliente - Sprint 1
  │   ├── P1 Planejamento
  │   ├── P1 Desenvolvimento
  │   └── P1 Revisão
  ├── Portal do cliente - Sprint 2
  │   ├── P1 Planejamento
  │   ├── P1 Desenvolvimento
  │   └── P1 Revisão
  └── Portal do cliente - Sprint 3
      ├── P1 Planejamento
      ├── P1 Desenvolvimento
      └── P1 Revisão
  ```
</Tab>

<Tab title="Condição">
  Um bloco `if` inclui parte da árvore só quando a condição é verdadeira:

  ```twig
  Planejamento
  Desenvolvimento
  {% if project.budget > 50000 %}
  Consultoria especializada
  -Análise avançada
  -Suporte dedicado
  {% endif %}
  Testes
  Entrega
  ```

  Com orçamento acima de 50.000, a árvore inclui "Consultoria especializada" e os dois netos. Com orçamento menor, esses três projetos não são criados.
</Tab>

<Tab title="Lista de dados">
  Um laço sobre uma lista cria um projeto por item. Aqui, um filho para cada usuário do projeto pai:

  ```twig
  {% for usuario in project.users %}
  Acompanhamento - {{ usuario.name }}
  {% endfor %}
  ```

  Se o projeto pai tem Ana e Bruno como usuários:

  ```text
  [Projeto pai]
  ├── Acompanhamento - Ana
  └── Acompanhamento - Bruno
  ```
</Tab>

<Tab title="Dados do projeto pai">
  Variáveis levam dados do projeto pai para o nome dos filhos:

  ```twig
  {{ project.customer.name|default('Cliente') }} - Fase 1
  -Análise de {{ project.customer.name|default('cliente') }}
  -Proposta para {{ project.customer.name|default('cliente') }}
  {{ project.customer.name|default('Cliente') }} - Fase 2
  -Implementação
  -Treinamento
  ```

  Se o cliente do projeto pai é "Transportadora Rio Claro":

  ```text
  [Projeto pai]
  ├── Transportadora Rio Claro - Fase 1
  │   ├── Análise de Transportadora Rio Claro
  │   └── Proposta para Transportadora Rio Claro
  └── Transportadora Rio Claro - Fase 2
      ├── Implementação
      └── Treinamento
  ```
</Tab>
</Tabs>

A linguagem completa está em [Sintaxe avançada](/guides/advanced/advanced-syntax).

## Exemplos completos

Os exemplos abaixo são estruturas inteiras, prontas para adaptar.

### Desenvolvimento de software

```text
>Análise de requisitos
-Entrevistas com as áreas
-Documentação de requisitos

>Design e arquitetura
-Design de interface
-Arquitetura do sistema

>Desenvolvimento
-Frontend
--Componentes
--Páginas
-Backend
--API
--Banco de dados

>Testes
-Testes unitários
-Testes de integração
-Testes de aceitação

>Implantação
-Configuração de ambiente
-Publicação em produção
```

Esta estrutura cria 20 projetos: 5 filhos, todos vinculados à etapa de destino, 11 netos e 4 bisnetos.

### Campanha de marketing

```text
>Pesquisa de mercado
-Análise da concorrência
-Pesquisa com clientes

>Estratégia
-Definição de público-alvo
-Desenvolvimento da mensagem

>Execução
-Produção de conteúdo
-Criação de materiais

>Divulgação
-Redes sociais
-E-mail marketing

>Análise
-Métricas de desempenho
-Relatório de resultados
```

### Sprints com sintaxe avançada

```twig
{% for i in 1..3 %}
>Sprint {{ i }}
-Planejamento da sprint {{ i }}
-Desenvolvimento da sprint {{ i }}
--Tarefas de frontend
--Tarefas de backend
-Testes da sprint {{ i }}
-Revisão da sprint {{ i }}
{% endfor %}

>Encerramento
-Documentação final
-Entrega ao cliente
```

Esta estrutura cria 24 projetos:

- 3 sprints com 7 projetos cada: a sprint, 4 netos e 2 bisnetos;
- o encerramento, com 2 netos.

## Limites e regras

Ao salvar a automação, a plataforma só confere se a estrutura foi preenchida. As outras regras são verificadas quando a ação executa, e uma falha aparece no [registro de execução](/guides/automation/logs):

- a sintaxe avançada precisa ser válida. Se não for, a ação registra `template_error_on_structure_parsing`;
- a hierarquia inteira vai até o nível 3, contado a partir do projeto raiz, como explica [Os quatro níveis](/guides/projects/project-hierarchy#os-quatro-níveis). Se a estrutura passar desse limite, a ação registra `hierarchy_depth_exceeds_maximum`.

O espaço disponível depende do nível do projeto pai:

| Nível do projeto pai | O que a estrutura pode ter |
| --- | --- |
| 0 (raiz) | Filhos, netos e bisnetos |
| 1 | Filhos e netos |
| 2 | Só filhos |

Ao executar, a ação segue estas regras:

- os projetos aparecem na árvore na mesma ordem da estrutura;
- só os projetos marcados com `>` são vinculados à etapa de destino;
- com modelo de projeto, cada projeto criado é uma cópia do modelo; sem modelo, o projeto nasce com as configurações básicas.

## Solução de problemas

Os problemas abaixo estão organizados pelo que você vê na tela.

<AccordionGroup>
<Accordion title="A automação não salva">
  O campo de estrutura está vazio. Escreva ao menos uma linha com o nome de um projeto e salve de novo.
</Accordion>

<Accordion title="A ação falhou no registro de execução">
  A estrutura não passou em uma das regras verificadas na execução. Confira o código do erro no [registro de execução](/guides/automation/logs):

  - `template_error_on_structure_parsing`: a sintaxe avançada tem um erro. Corrija o trecho entre `{{ }}` ou `{% %}`;
  - `hierarchy_depth_exceeds_maximum`: a estrutura passa do nível 3 da hierarquia. Tire da estrutura o nível que passa do limite;
  - `project_not_found_for_attach`: no modo de vincular, uma linha não corresponde ao código de um projeto da empresa. Confira o código.
</Accordion>

<Accordion title="Os projetos não aparecem na etapa">
  Só os projetos marcados com `>` são vinculados à etapa de destino. Adicione o prefixo `>` aos projetos que devem ir para a etapa:

  ```text
  >Projeto que vai para a etapa
  Projeto que não vai para a etapa
  ```
</Accordion>

<Accordion title="A árvore saiu com os níveis errados">
  Os hífens não correspondem ao nível desejado. Confira:

  - filhos não têm prefixo;
  - netos têm um `-`;
  - bisnetos têm dois `--`.

  ```text
  Correto:
  Filho
  -Neto
  --Bisneto

  Incorreto:
  -Filho
  Neto
  ---Bisneto
  ```
</Accordion>

<Accordion title="Os projetos foram criados sem o conteúdo do modelo">
  Nenhum modelo estava selecionado em **Projeto modelo**, então os projetos foram criados do zero. Selecione o modelo na ação e salve a automação de novo.
</Accordion>
</AccordionGroup>
