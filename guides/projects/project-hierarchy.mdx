A hierarquia de projetos organiza projetos em uma árvore: um projeto pode ter outros projetos abaixo dele, que são os filhos. Use a hierarquia quando um trabalho grande precisa ser dividido em partes menores, cada uma acompanhada como um projeto próprio.

Esta página explica os níveis, as regras que a plataforma verifica e as operações que mudam a estrutura. Para montar uma árvore inteira de uma vez por automação, veja [Hierarquia de projetos automatizada](/guides/automation/automated-hierarchy).

## Pai, filho, raiz e folha

A hierarquia usa quatro termos para descrever a posição de um projeto:

| Termo | O que é |
| --- | --- |
| **Projeto pai** | Um projeto que tem outros projetos diretamente abaixo dele |
| **Projeto filho** | Um projeto que está diretamente abaixo de um projeto pai. Representa uma parte ou subdivisão do pai |
| **Projeto raiz** | Um projeto sem pai. É o topo da árvore |
| **Projeto folha** | Um projeto sem filhos. É o fim de um ramo da árvore |

Um mesmo projeto pode ter mais de um papel: um filho que tem filhos também é pai, e uma raiz sem filhos também é folha.

## Os quatro níveis

A hierarquia aceita até **4 níveis**, numerados de 0 a 3:

| Nível | Nome | Posição |
| --- | --- | --- |
| 0 | Raiz | O topo da árvore, sem pai |
| 1 | Filho | Diretamente abaixo da raiz |
| 2 | Neto | Filho de um filho |
| 3 | Bisneto | Filho de um neto. É o último nível permitido |

Um bisneto não pode ter filhos. O número de filhos por projeto é ilimitado. Os valores estão reunidos em [Limites da plataforma](/guides/fundamentals/limits).

Os quatro níveis acompanham as camadas da operação: estratégico, tático, operacional e microatividade. Veja [o modelo mental](/guides/fundamentals/mental-model) para entender essa relação.

## Regras que a plataforma verifica

A plataforma verifica estas regras automaticamente e recusa a operação que violaria alguma delas:

| Regra | O que significa |
| --- | --- |
| Mesma empresa | Pai e filho podem ser quaisquer projetos da mesma empresa |
| Sem ciclos | Um projeto não pode ficar abaixo de um dos próprios descendentes. Se o projeto A é pai do projeto B, B não pode ser pai de A |
| Sem autorreferência | Um projeto não pode ser pai de si mesmo |
| Limite de profundidade | Nenhuma operação pode deixar um projeto abaixo do nível 3 (bisneto) |

## Ver a estrutura

A hierarquia pode ser consultada de três formas. Os exemplos abaixo usam a obra de um shopping center dividida em etapas construtivas.

## Mudar a estrutura

A estrutura pode ser reorganizada a qualquer momento. Estas são as operações disponíveis:

| Operação | O que faz |
| --- | --- |
| Vincular um filho | Coloca um projeto existente diretamente abaixo de outro |
| Desvincular um filho | Tira o projeto de baixo do pai. O projeto vira raiz e mantém os próprios filhos |
| Promover a raiz | Desliga o projeto do pai. Os filhos dele acompanham a mudança e mantêm as posições entre si |
| Mover para outro pai | Coloca o projeto, com toda a descendência dele, abaixo de outro pai |

Ao mover um projeto, a plataforma considera a descendência inteira dele. Se algum descendente passaria do nível 3, a movimentação é recusada. Nesse caso, escolha um pai em um nível mais alto ou reduza a profundidade do ramo antes de mover.

Reorganizar a hierarquia não altera o conteúdo dos projetos.

## Planejar a estrutura

Pensar na árvore antes de criar os projetos evita reorganizações por causa do limite de níveis:

- **Comece pelo projeto raiz.** Ele é o trabalho mais abrangente, que engloba todos os outros.
- **Defina os filhos diretos.** Eles são as grandes divisões do trabalho, por área ou por momento.
- **Conte os níveis.** Se a divisão pede mais de quatro níveis, o que ficaria no quinto costuma ser microtarefa, que cabe melhor em um [checklist avulso](/guides/projects/overview#checklists-avulsos). Outra saída é separar o trabalho em mais de uma árvore.
- **Dê nomes que mostrem a função.** Nomes descritivos, no mesmo padrão entre projetos do mesmo nível, deixam o caminho hierárquico legível.
