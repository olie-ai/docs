A busca avançada filtra e ordena listagens com critérios enviados no corpo de uma requisição `POST`. Esta página mostra a estrutura dos filtros e das ordenações, os operadores aceitos, como descobrir os campos disponíveis e como tratar os erros.

A busca avançada está disponível em três endpoints:

- `POST /api/management/projects/search`
- `POST /api/management/customers/search`
- `POST /api/management/contacts/search`

Para filtros simples enviados na URL, como `filter[status]=active`, veja [Filtros básicos](/api-reference/general/basic-filters).

## Primeira busca

Esta requisição completa, com autenticação, busca os projetos com orçamento maior que 10.000:

```bash
curl -X POST "https://api.olie.ai/api/management/projects/search" \
  -H "Authorization: Bearer {{token_de_acesso}}" \
  -H "Content-Type: application/json" \
  -d '{
    "filters": [
      { "field": "budget", "operator": "greater_than", "value": 10000 }
    ]
  }'
```

A resposta traz a lista em `projects` e os dados de paginação em `meta`, como descrito em [Paginação](/api-reference/general/pagination).

## Estrutura da requisição

O corpo da requisição é um objeto JSON com quatro campos, todos opcionais:

<ParamField body="filters" type="array">
Lista de filtros. Cada filtro define o campo, o operador, o valor e como ele se combina com o filtro anterior.
</ParamField>

<ParamField body="sorting" type="array">
Lista de ordenações, na ordem de prioridade. Cada ordenação define o campo e a direção.
</ParamField>

<ParamField body="page" type="integer" default="1">
Número da página, a partir de 1. Veja [Paginação](/api-reference/general/pagination).
</ParamField>

<ParamField body="perPage" type="integer" default="30">
Quantidade de itens por página, de 1 a 100. Veja [Paginação](/api-reference/general/pagination).
</ParamField>

## Estrutura de um filtro

Cada item de `filters` tem estes campos:

<ParamField body="filters[].field" type="string" required>
Nome do campo a filtrar. Os campos aceitos variam por endpoint: veja [Descobrindo campos disponíveis](#descobrindo-campos-disponíveis).
</ParamField>

<ParamField body="filters[].operator" type="string" required>
Operador de comparação. Os valores aceitos estão em [Operadores de comparação](#operadores-de-comparação).
</ParamField>

<ParamField body="filters[].value" type="string | number | boolean | array | null">
Valor a comparar. O tipo depende do campo e do operador.
</ParamField>

<ParamField body="filters[].logical_operator" type="string" default="and">
Como o filtro se combina com o anterior: `and` ou `or`.
</ParamField>

<ParamField body="filters[].arguments" type="array">
Argumentos extras que alguns campos exigem, como o campo do formulário em um filtro por resposta de formulário. Veja [Argumentos adicionais](#argumentos-adicionais).
</ParamField>

## Operadores de comparação

O campo `operator` aceita os valores da tabela. Nem todo campo aceita todos os operadores: a lista de cada campo está em [Descobrindo campos disponíveis](#descobrindo-campos-disponíveis).

| Operador | Significado | Grupo |
| --- | --- | --- |
| `equals` | Igual a | Igualdade |
| `not_equals` | Diferente de | Igualdade |
| `contains` | Contém o texto (busca parcial) | Texto |
| `not_contains` | Não contém o texto | Texto |
| `greater_than` | Maior que | Número e data |
| `greater_than_or_equals` | Maior ou igual a | Número e data |
| `less_than` | Menor que | Número e data |
| `less_than_or_equals` | Menor ou igual a | Número e data |
| `is_null` | Campo vazio (nulo) | Nulo |
| `is_not_null` | Campo preenchido (não nulo) | Nulo |

## Combinar filtros com and e or

O campo `logical_operator` define como cada filtro se combina com o anterior:

- **`and`** (padrão): o item precisa atender aos dois filtros.
- **`or`**: o item precisa atender a pelo menos um dos dois filtros.

O `logical_operator` vale a partir do segundo filtro. No primeiro filtro, a API ignora o valor.

<Tip>
Use o mesmo operador lógico em todos os filtros da busca, só `and` ou só `or`. Misturar os dois na mesma lista pode trazer resultados diferentes do esperado.
</Tip>

## Estrutura de uma ordenação

Cada item de `sorting` tem estes campos:

<ParamField body="sorting[].field" type="string" required>
Nome do campo usado na ordenação. Os campos aceitos variam por endpoint: veja [Descobrindo campos disponíveis](#descobrindo-campos-disponíveis).
</ParamField>

<ParamField body="sorting[].direction" type="string" required>
Direção da ordenação: `asc` (crescente) ou `desc` (decrescente).
</ParamField>

<ParamField body="sorting[].arguments" type="array">
Argumentos extras que algumas ordenações exigem.
</ParamField>

## Argumentos adicionais

Alguns campos só funcionam com um contexto a mais. Por exemplo, para filtrar projetos pela resposta de um formulário (campo `answer_pool`), você precisa dizer qual campo do formulário comparar. Esse contexto vai em `arguments`.

Os argumentos de cada campo aparecem na resposta do endpoint de metadados, descrita em [Descobrindo campos disponíveis](#descobrindo-campos-disponíveis).

## Exemplos

Os exemplos usam a busca de projetos. Na busca de clientes e de contatos, a estrutura é a mesma e só mudam os campos.

<Tabs>
<Tab title="Dois filtros com and">
Busca os projetos em andamento (`status` igual a `1`) cujo nome contém "Implantação":

```http
POST /api/management/projects/search
Content-Type: application/json

{
  "filters": [
    { "field": "name", "operator": "contains", "value": "Implantação" },
    { "field": "status", "operator": "equals", "value": 1, "logical_operator": "and" }
  ]
}
```
</Tab>

<Tab title="Dois filtros com or">
Busca os projetos criados a partir de 1º de janeiro de 2026 **ou** com orçamento maior que 10.000:

```http
POST /api/management/projects/search
Content-Type: application/json

{
  "filters": [
    { "field": "created_at", "operator": "greater_than_or_equals", "value": "2026-01-01T00:00:00Z" },
    { "field": "budget", "operator": "greater_than", "value": 10000, "logical_operator": "or" }
  ]
}
```
</Tab>

<Tab title="Filtros, ordenação e paginação">
Busca os projetos em andamento com "Implantação" no nome e orçamento maior que 10.500, do mais recente para o mais antigo, 30 por página:

```http
POST /api/management/projects/search
Content-Type: application/json

{
  "filters": [
    { "field": "name", "operator": "contains", "value": "Implantação" },
    { "field": "status", "operator": "equals", "value": 1, "logical_operator": "and" },
    { "field": "budget", "operator": "greater_than", "value": 10500, "logical_operator": "and" }
  ],
  "sorting": [
    { "field": "created_at", "direction": "desc" }
  ],
  "page": 1,
  "perPage": 30
}
```
</Tab>
</Tabs>

## Descobrindo campos disponíveis

Cada endpoint aceita um conjunto próprio de campos, operadores e argumentos. Para consultar esse conjunto, use o endpoint de metadados:

```http
GET /api/management/system/params/{model_name}
```

Troque `{model_name}` pelo objeto da busca: `project`, `customer` ou `contact`. A resposta abaixo, da busca de projetos, mostra três dos filtros e parte das ordenações:

```json
{
  "response": true,
  "params": {
    "filters": [
      {
        "name": "name",
        "input_type": "text",
        "operators": ["equals", "not_equals", "contains", "not_contains"],
        "options": [],
        "arguments": [],
        "hydrate": null
      },
      {
        "name": "status",
        "input_type": "text",
        "operators": ["equals", "not_equals"],
        "options": [
          { "label": "Em andamento", "value": 1 },
          { "label": "Concluído", "value": 2 },
          { "label": "Arquivado", "value": 3 },
          { "label": "Paralisado", "value": 4 }
        ],
        "arguments": [],
        "hydrate": null
      },
      {
        "name": "answer_pool",
        "input_type": "text",
        "operators": [
          "equals", "not_equals", "contains", "not_contains",
          "greater_than", "greater_than_or_equals", "less_than", "less_than_or_equals",
          "is_null", "is_not_null"
        ],
        "options": [],
        "arguments": [
          {
            "id": "answer_pool_edge",
            "label": "Campo",
            "required": true,
            "modelClass": "App\\Models\\FormEdge",
            "hydrate": {
              "route": "/api/management/get-forms",
              "options": "forms",
              "key": "id",
              "label": "label",
              "children_key": "edges",
              "children_label": "title"
            }
          }
        ],
        "hydrate": null
      }
    ],
    "sorting": [
      { "name": "name", "arguments": [] },
      { "name": "impact", "arguments": [] },
      { "name": "created_at", "arguments": [] }
    ]
  }
}
```

A resposta real traz todos os filtros e todas as ordenações do objeto.

Cada item de `params.filters` descreve um campo que você pode usar em `filters[].field`:

| Campo | O que informa |
| --- | --- |
| `name` | O nome a usar em `filters[].field`. |
| `input_type` | O tipo de valor esperado, como `text`, `number` ou `datetime-local`. |
| `operators` | Os operadores aceitos por esse campo. |
| `options` | Os valores fixos aceitos, com rótulo e valor, quando o campo tem uma lista fechada. Envie o `value` da opção. |
| `arguments` | Os argumentos que o campo aceita. `required: true` indica argumento obrigatório, e `hydrate` diz em qual endpoint buscar os valores possíveis. |
| `hydrate` | Onde buscar as opções do próprio campo, ou `null` quando não se aplica. |

Os itens de `params.sorting` trazem o `name` a usar em `sorting[].field`.

## Tratamento de erros

Quando um filtro não é válido, a API responde com HTTP 422, `message: "validation_errors"` e o detalhe em `validation`, como em qualquer [erro de validação](/api-reference/general/response-structure#erros-de-validação). Consulte o [endpoint de metadados](#descobrindo-campos-disponíveis) para ver o que o campo aceita.

### Campo inválido

A API recusa o filtro quando `field` não está na lista de campos do endpoint. A mensagem cita o nome enviado:

```json
{
  "response": false,
  "message": "validation_errors",
  "error": "O campo nonExistsFilterField selecionado é inválido.",
  "validation": {
    "field": ["O campo nonExistsFilterField selecionado é inválido."]
  }
}
```

Para resolver, use em `field` um dos valores de `name` em `params.filters`.

### Operador inválido

A API recusa o filtro quando `operator` não está na lista `operators` daquele campo:

```json
{
  "response": false,
  "message": "validation_errors",
  "error": "The selected operator is invalid.",
  "validation": {
    "operator": ["The selected operator is invalid."]
  }
}
```

Para resolver, troque o operador por um dos valores de `operators` do campo.

### Argumento obrigatório ausente

A API recusa o filtro quando o campo tem um argumento com `required: true` e o filtro não traz `arguments`. No exemplo, o filtro por resposta de formulário (`answer_pool`) chegou sem o campo do formulário:

```json
{
  "response": false,
  "message": "validation_errors",
  "error": "Argument zero must be id of edge",
  "validation": {
    "answer_pool": ["Argument zero must be id of edge"]
  }
}
```

Para resolver, envie em `arguments` os argumentos obrigatórios listados para o campo no endpoint de metadados.
