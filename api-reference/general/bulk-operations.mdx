A API tem dois endpoints para alterar vários registros em uma única requisição: a atualização em lote e a movimentação em lote entre etapas. Esta página mostra o corpo de cada um, como ler o resultado e como tratar os erros.

Os dois endpoints se comportam de formas **opostas** diante de um erro:

| Endpoint | Em caso de erro |
| --- | --- |
| `POST /api/management/system/bulk-update/{model_name}` | **Parcial.** O que dá certo fica gravado; o que falha é pulado. |
| `POST /api/management/project-bulk-step-move` | **Tudo ou nada.** Para no primeiro erro e nenhuma movimentação é confirmada. |

<Warning>
Escolher o endpoint errado muda o que acontece com os dados. Leia as duas seções antes de decidir.
</Warning>

## Atualização em lote

A atualização em lote aplica os mesmos valores a todos os registros da lista:

```http
POST /api/management/system/bulk-update/{model_name}
```

### Modelos aceitos

O `model_name` do caminho aceita dois valores:

| `model_name` | O que atualiza |
| --- | --- |
| `project` | Projetos. |
| `answer_pool` | Respostas de formulários dinâmicos. |

Qualquer outro valor devolve HTTP **422**, com `message: "validation_errors"` e o motivo em `validation.model`:

- **Modelo ainda não suportado** (por exemplo, `contact`): `messages.model_not_supported_yet`.
- **Modelo que não existe:** `Model was not found`.

Para resolver, use `project` ou `answer_pool` no caminho. Para alterar vários registros de outro tipo, faça uma requisição por registro.

### Corpo da requisição

O corpo é um objeto com a lista de `ids` e, no mesmo nível, os campos a aplicar em todos eles. Este exemplo marca três projetos como em andamento, com impacto 8, e troca uma etiqueta por outra:

```json
{
  "ids": [
    "019b140c-235d-73ee-96df-3d2afbf7d13d",
    "019b140b-e38e-7207-8016-9bfe6fa1d02f",
    "019b140b-a1c2-7d44-8e0f-5b6c7d8e9f10"
  ],
  "status": 1,
  "impact": 8,
  "tags": { "to_add": [12], "to_rem": [7] }
}
```

<ParamField body="ids" type="array" required>
Lista dos identificadores a atualizar. Não pode estar vazia e não aceita valores repetidos. **Não há teto de quantidade.**
</ParamField>

Como não há teto, um lote muito grande pode passar do tempo limite da requisição. Prefira lotes moderados e acompanhe o resultado.

#### Campos de `project`

Os campos simples são aplicados diretamente no projeto:

| Campo | Tipo |
| --- | --- |
| `name` | string |
| `description` | string |
| `impact` | integer (1 a 10) |
| `contact_id` | integer |
| `customer_id` | uuid |
| `status` | integer (`1` em andamento, `2` concluído, `3` arquivado, `4` parado) |
| `budget` | numeric |
| `is_template` | boolean |
| `parent_id` | uuid ou `null` |

As relações abaixo usam o formato `{ "to_add": [...], "to_rem": [...] }`. Envie **as duas chaves**, mesmo que uma delas vá vazia:

| Campo | Conteúdo |
| --- | --- |
| `funnels` | ids de funis a vincular / desvincular |
| `groups` | ids de grupos de projeto |
| `tags` | ids de etiquetas |
| `childrens` | ids de projetos filhos |

As demais relações têm formato próprio:

| Campo | Formato |
| --- | --- |
| `funnel_status` | `{ "project_funnel_id": 10, "funnel_status_id": 3 }` |
| `forecast_dates` | lista de `{ "project_funnel_id": 10, "date": "2026-10-01" }` |
| `users` | lista de `{ "user_id": "uuid", "role": "...", "action": "..." }` |
| `form_answers` | respostas de formulário do projeto |

<Warning>
**Campos desconhecidos são ignorados sem aviso.** Um erro de digitação (`statsu` em vez de `status`) não gera erro: a requisição responde 200 com todos os itens em `successCount` e nada é alterado. Confira o resultado relendo um dos registros.
</Warning>

#### Campos de `answer_pool`

Com `answer_pool`, o lote grava as mesmas respostas de formulário em todos os registros da lista. Este exemplo responde o campo 30 do formulário do objeto projeto em dois projetos:

```json
{
  "ids": [
    "019b140c-235d-73ee-96df-3d2afbf7d13d",
    "019b140b-e38e-7207-8016-9bfe6fa1d02f"
  ],
  "form_answers": [
    { "id": 30, "answer": "Indicação" }
  ],
  "target": {
    "pivot_class": "App\\Models\\Project",
    "form_id": 21,
    "father_class": "App\\Models\\Project"
  }
}
```

<ParamField body="form_answers" type="array" required>
As respostas a gravar, no mesmo formato usado na [gravação individual](/api-reference/general/form-answer-pivot#gravar-respostas): cada item tem o `id` do campo e a `answer`.
</ParamField>

<ParamField body="target" type="object" required>
Endereço do formulário, o [pivot](/api-reference/general/form-answer-pivot). Exige `pivot_class`, `form_id` e `father_class`. A API usa cada item de `ids` como o registro alvo, então você não envia `father_id`.
</ParamField>

O lote também grava formulários de etapa e de funil. Nesses casos, os `ids` continuam sendo ids de projeto, e o `target` leva o id da etapa ou do funil:

| `pivot_class` | Formulário | Campo extra em `target` |
| --- | --- | --- |
| `App\Models\Project` | Do objeto projeto | nenhum |
| `App\Models\ProjectStepForm` | De uma etapa | `funnel_step_id` |
| `App\Models\ProjectFunnelAssignment` | De um funil | `project_funnel_id` |

### Resposta

A resposta tem HTTP **200** mesmo quando alguns itens falham. O resultado do lote está em `result`:

```json
{
  "response": true,
  "result": {
    "successCount": 2,
    "failedCount": 1,
    "fails": [
      { "id": "019b140b-a1c2-7d44-8e0f-5b6c7d8e9f10", "error": "The step has requirements not filled" }
    ]
  }
}
```

<ResponseField name="result.successCount" type="integer">
Quantos itens foram atualizados com sucesso.
</ResponseField>

<ResponseField name="result.failedCount" type="integer">
Quantos itens falharam.
</ResponseField>

<ResponseField name="result.fails" type="array">
Um objeto por falha, com `id` e `error`. Quando a falha é de permissão, o objeto também traz `permission`, com a permissão que faltou.
</ResponseField>

A resposta não lista os itens que deram certo. Para saber quais passaram, compare: são os de `ids` que não aparecem em `fails`.

### Falha no meio de um item

A API processa item a item, mas **não desfaz as alterações de um item que falhou**. Se um projeto falhar depois de receber parte das alterações, a parte já aplicada permanece. Por exemplo, o campo simples é gravado e a relação seguinte falha.

<Warning>
Um `id` em `fails` não significa que nada mudou nesse registro, e sim que a operação não terminou. Releia o registro antes de processá-lo de novo.
</Warning>

### Concorrência

A API processa um lote por usuário de cada vez. Se outro lote do mesmo usuário estiver em andamento, a requisição responde com HTTP **409**:

```json
{
  "response": false,
  "message": "bulk_operation_in_progress",
  "error": "Another bulk operation is already in progress"
}
```

A trava vale por usuário e por empresa e só se aplica a lotes com mais de um item. Um lote de um item só nunca recebe 409.

Ao receber 409, espere o lote anterior terminar e repita a requisição. Com o mesmo token, envie um lote de cada vez.

## Movimentação em lote entre etapas

A movimentação em lote move vários projetos para a mesma etapa de funil:

```http
POST /api/management/project-bulk-step-move
```

### Corpo da requisição

Este exemplo move dois projetos para a etapa 42 e os desvincula das outras etapas do mesmo funil:

```json
{
  "project_ids": [
    "019b140c-235d-73ee-96df-3d2afbf7d13d",
    "019b140b-e38e-7207-8016-9bfe6fa1d02f"
  ],
  "step_id": 42,
  "unlink_others": true,
  "force_funnel_link": false
}
```

<ParamField body="project_ids" type="array" required>
Lista de IDs (UUID) dos projetos.
</ParamField>

<ParamField body="step_id" type="integer" required>
Etapa de destino.
</ParamField>

<ParamField body="unlink_others" type="boolean">
Quando `true`, desvincula o projeto das outras etapas do mesmo funil.
</ParamField>

<ParamField body="force_funnel_link" type="boolean">
Quando `true`, vincula o projeto ao funil da etapa caso ele ainda não esteja vinculado.
</ParamField>

Projetos que já estão na etapa de destino são ignorados, sem erro.

### Tudo ou nada

Este endpoint **para no primeiro erro**, e nenhuma movimentação do lote é confirmada, nem a dos projetos processados antes da falha.

A resposta de erro segue o [formato padrão](/api-reference/general/response-structure) e informa o motivo, com o detalhe da restrição ou do requisito que barrou a movimentação. As regras por trás desses erros estão em [Restrições de etapa](/guides/funnels/restrictions) e [Requisitos de etapa](/guides/funnels/requirements).

| `message` | Motivo | Como resolver |
| --- | --- | --- |
| `step_requirements_not_filled` | A etapa tem requisitos não preenchidos. Acompanha `requirements`. | Preencha os itens listados em `requirements` antes de mover. |
| `incoming_restrictions` | A etapa de destino restringe de onde o projeto pode vir. Acompanha `restrictions`. | Mova o projeto a partir de uma etapa aceita em `restrictions` ou ajuste a restrição. |
| `outgoing_restrictions` | A etapa de origem restringe para onde o projeto pode ir. Acompanha `restrictions`. | Escolha uma etapa de destino aceita em `restrictions` ou ajuste a restrição. |
| `blocked_by_existing_step_blocking` | O projeto tem etiqueta ou status que a etapa bloqueia. Acompanha `step_blockings`. | Remova a etiqueta ou o status listado em `step_blockings`, ou ajuste o bloqueio. |
| `project_funnel_not_linked_with_project` | O projeto não está vinculado ao funil da etapa. | Envie `force_funnel_link: true` ou vincule o projeto ao funil antes. |
| `project_funnel_not_active` | O funil da etapa está inativo. | Ative o funil ou escolha uma etapa de outro funil. |

O erro descreve o motivo, mas **não diz qual projeto falhou**. Para descobrir qual projeto barrou o lote, mova um projeto de cada vez com `POST /api/management/funnel-steps/{funnel_step_id}/projects`. O projeto que reproduzir o erro é o responsável.

### Concorrência na movimentação

A movimentação em lote usa a mesma trava da atualização em lote: um lote por usuário de cada vez, com HTTP **409** e `bulk_operation_in_progress` quando já existe outro em andamento. Um lote de atualização em curso também bloqueia um lote de movimentação do mesmo usuário, e vice-versa.

## Boas práticas

Estes cuidados evitam as falhas mais comuns nos lotes:

- **Escolha o endpoint pelo comportamento de erro.** Se o lote inteiro precisa dar certo ou falhar junto, use a movimentação entre etapas. Se você quer aplicar o que for possível e tratar o resto depois, use a atualização em lote.
- **Confira o nome dos campos.** Na atualização em lote, um campo escrito errado é ignorado sem aviso. Valide o corpo antes de rodar sobre muitos registros.
- **Leia sempre o `result`.** Um `successCount` igual ao total garante só que nenhum item deu erro, e não que os campos certos foram aplicados.
- **Envie um lote de cada vez.** Com o mesmo usuário, o segundo lote recebe 409. Organize uma fila do seu lado.
